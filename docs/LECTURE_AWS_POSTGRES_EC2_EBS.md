# Lecture: Building the FMIS PoC Database on AWS

> Self-managed PostgreSQL on EC2 + EBS, provisioned with Terraform, administered with SSM,
> secured by security groups, backed up with DLM snapshots, and migrated with Atlas.

This document is written for someone seeing cloud system design for the first time. It explains
not just *what* we built, but *why* each decision was made, how each AWS service works, and what
we learned from the mistakes we hit along the way.

## 1. The 30-second summary

We created one EC2 virtual machine running PostgreSQL 16, in AWS's default VPC in Singapore
(`ap-southeast-1`). Its data lives on a separate encrypted disk (an EBS volume) so the data
survives if the machine is stopped or replaced. A security group makes port 5432 reachable
**only** from a second security group reserved for the future application tier. Admin access is
**SSM-only** — no SSH port, no SSH key. Credentials are generated by Terraform and stored in
Secrets Manager. A Data Lifecycle Manager (DLM) policy snapshots the data disk daily and keeps 7
days. The whole thing is declared in Terraform under `infra/`, and Atlas migrations were applied

## 2. AWS building blocks (the vocabulary)

Before reading the Terraform, here are the services we used, in plain language.

### 2.1 Region and Availability Zone (AZ)

A **region** is a geographic cluster of data centers (here, Singapore). An **Availability Zone**
is an isolated data center within a region (`ap-southeast-1a`, `ap-southeast-1b`, ...). You place
resources in a region and, for high availability, spread them across AZs. Our PoC uses a single AZ
because a single database instance cannot span AZs anyway — higher availability would require a
replica in another AZ, which we deliberately skipped for a one-week proof of concept.

### 2.2 VPC, subnets, internet gateway, route tables

A **VPC (Virtual Private Cloud)** is your own private network inside AWS. It has a CIDR block, e.g.
`172.31.0.0/16` (65,536 addresses). A **subnet** is a slice of that range tied to one AZ, e.g.
`172.31.16.0/20` (4,096 addresses) in `ap-southeast-1b`.

The default subnet layout:

```
VPC 172.31.0.0/16
├── subnet-083cc86e  ap-southeast-1b  172.31.16.0/20
└── subnet-41856109  ap-southeast-1a  172.31.32.0/20
```

An **internet gateway (IGW)** is the door between the VPC and the public internet. A **route
table** decides where traffic goes:

- `172.31.0.0/16 -> local` (talk to other machines in the VPC)
- `0.0.0.0/0 -> igw-...` (everything else goes to the internet)

A subnet is "public" if its route table points to an internet gateway and instances opt into
public IPs (`MapPublicIpOnLaunch = true`). In our default VPC, **both subnets are public**.

### 2.3 Security groups (SGs)

A **security group** is a stateful firewall attached to an instance (or other resource). Key
properties:

- It has **allow rules only** — there is no "deny" rule. Anything not allowed is dropped.
- It is **stateful**: if you allow inbound 5432, the response traffic is automatically allowed back out.
- Rules can reference another **security group** instead of an IP range. That is the trick we use:
  "allow 5432 from `sg-0f962929f956ecf62`" means "allow any instance that belongs to the app-tier SG."

Contrast with **network ACLs** (subnet-level, stateless) — we did not touch those; the default
VPC NACLs allow everything, and the SGs do the real enforcement.

### 2.4 EC2 (Elastic Compute Cloud)

An **EC2 instance** is a virtual machine. You choose:

- an **AMI** (Amazon Machine Image — the OS template; we use Amazon Linux 2023),
- an **instance type** (`t3.micro`: 2 vCPU burstable, 1 GiB RAM),
- a **subnet**, a **security group**, and an **IAM instance profile**,
- `user_data` (a script that runs on first boot — this is how we install PostgreSQL).

Instances are disposable. The root disk (`root_block_device`) is deleted when the instance is
terminated. Anything you want to keep should live elsewhere — which is exactly why the database
data lives on a **separate EBS volume**.

### 2.5 EBS (Elastic Block Store)

An **EBS volume** is a network-attached virtual disk. Important properties:

- It is independent of the instance lifecycle. We can terminate the instance and keep the data.
- It must be in the **same AZ** as the instance that attaches to it.
- Types: `gp3` (general purpose SSD, cheap baseline) is what we use.
- It can (and should) be **encrypted** at rest. We set `encrypted = true`.
- Snapshots of volumes are stored in S3-managed storage, are **incremental**, and survive the
  volume's deletion.

On Nitro-based instances, Linux sees the attached volume as an NVMe disk (`/dev/nvme1n1`) even
though you request `/dev/sdf`. Our bootstrap script uses `blkid` (which follows the mapping) and
mounts by filesystem UUID rather than by device name, so this is not a problem.

### 2.6 IAM roles and instance profiles

**IAM** is AWS's permissions system. Rather than putting AWS credentials on the instance, we attach
a **role** to it via an **instance profile**. The EC2 service "assumes" the role, and the instance's
SDK/CLI calls are signed with temporary credentials it fetches from the instance metadata service.

Our instance role has two permissions:

1. `AmazonSSMManagedInstanceCore` — lets the SSM agent register and open sessions.
2. A tiny inline policy: `secretsmanager:GetSecretValue` on exactly one secret.

This is the **least-privilege** principle: the instance can read its own database password and
nothing else in AWS.

### 2.7 SSM (AWS Systems Manager) and Session Manager

**SSM** is a fleet-management service. A small **SSM agent** runs on the instance and connects
*outbound* (HTTPS/443) to the SSM service. Because the connection is initiated by the instance, you
never need to open an inbound management port.

Once an instance is registered, you can:

- **Start a session** (`aws ssm start-session`): an interactive shell, as if you SSH'd in, but over
  AWS IAM-authorized channels. No key, no port 22.
- **Run a command** (`aws ssm send-command`): non-interactive, scriptable, returns stdout/stderr.
- **Forward a port** (`AWS-StartPortForwardingSession`): tunnel, say, your laptop's `localhost:15432`
  to the instance's `5432`. This is how we reach a private database from a laptop without exposing it.

### 2.8 Secrets Manager

**AWS Secrets Manager** stores secrets (passwords, connection strings, API keys) encrypted with KMS,
with fine-grained IAM access and optional rotation. We generate a random 32-character password in
Terraform, store it as a JSON secret (`username`, `password`, `engine`, `port`, `dbname`), and the
instance reads it at boot using its IAM role. The password is never baked into the AMI or the
Terraform `user_data` text.

### 2.9 DLM (Data Lifecycle Manager)

**DLM** automates EBS snapshots. You define a policy with:

- **Target tags** — which volumes to snapshot (we tag the volume `Snapshot=daily`),
- a **schedule** (daily at 02:00 UTC),
- a **retention rule** (keep the last 7),
- an **execution role** that DLM assumes to create/delete snapshots.

DLM is free; you pay only for the snapshot storage.

```
                    |   |  SG: fmis-api-db          |   |
                    |   |      (sg-0bbd...)         |   |
                    |   |            |              |   |
                    |   |      /dev/sdf (gp3, enc.) |   |
                    |   +------------|--------------+   |
                    |                |                  |
                    |                v                  |

                    |      tag Snapshot=daily           |
                    |          ^                        |
                    |          | snapshots              |
                    |      DLM policy-096b...           |
                    |      daily 02:00 UTC, keep 7      |
                    +-----------------------------------+
                              ^
                              | ingress 5432 ONLY from
                              | sg-0f962929f956ecf62
                    +----------------------------+
                    | app-tier SG (fmis-api-     |
                    | app-tier), attached to     |
                    | future ECS/Fargate tasks   |
                    +----------------------------+

     Admin path (out of band, no network ingress):
     engineer --(HTTPS)--> AWS SSM service <--(HTTPS, outbound)--> SSM agent on EC2
```

Read this diagram as three independent questions:

1. **Who can reach the database?** Only whatever carries the app-tier SG. Today that is nothing
   (the app tier is future work), so the database is effectively sealed.
2. **Who can administer the host?** Anyone with IAM permission to start an SSM session — not
   anyone with network reach.
3. **How is data preserved?** Separate EBS volume + daily DLM snapshots.

## 4. How the VPC was set up

### 4.1 What actually exists (verified live)

We did **not create a VPC**. The account already had the AWS **default VPC**, so we discovered it
with a Terraform *data source* and placed resources inside it.

```
Default VPC:        vpc-624e4d05        172.31.0.0/16
Default subnets:    subnet-083cc86e     ap-southeast-1b   172.31.16.0/20   public
                    subnet-41856109     ap-southeast-1a   172.31.32.0/20   public
Internet gateway:   igw-bc4764d8        attached, available
Main route table:   rtb-61f06707        172.31.0.0/16 -> local
                                        0.0.0.0/0     -> igw-bc4764d8
```

### 4.2 What a "default VPC" is

When AWS accounts are created (in older accounts, like this one, automatically), AWS builds one VPC
per region for you:

- one `/16` CIDR block (`172.31.0.0/16`),
- one public subnet per Availability Zone, each with `MapPublicIpOnLaunch = true`,
- an internet gateway attached,
- a main route table routing `0.0.0.0/0` to that gateway,
- a default security group and default network ACL.

It exists so you can launch an internet-reachable instance immediately, with zero networking work.

### 4.3 How Terraform "sets it up" without creating it

In `infra/data.tf`:

```hcl
data "aws_vpc" "default" {
  default = true
}

data "aws_subnets" "default" {
  filter { name = "default-for-az" values = ["true"] }
  filter { name = "vpc-id"         values = [data.aws_vpc.default.id] }
}

data "aws_subnet" "db" {
  id = sort(data.aws_subnets.default.ids)[0]
}
```

A `data` block **reads** existing infrastructure; a `resource` block **creates and owns** it. That
distinction matters: because we only *read* the VPC, `terraform destroy` will never try to delete
it. Then the security groups are created *inside* the discovered VPC:

```hcl
vpc_id = data.aws_vpc.default.id
```

`sort(...)[0]` picks one subnet deterministically (alphabetic order, which happens to be the
`ap-southeast-1b` one). A production design would spread the app tier across both AZs and pick a
private subnet deliberately.

### 4.4 Why the default VPC (and the tradeoff)

The design doc's target Phase 4 architecture is a **dedicated VPC + ALB**. We deliberately deviated
for the PoC:

| | Custom VPC (design doc target) | Default VPC (what we did) |
|---|---|---|
| Setup effort | Subnets, IGW, NAT, route tables, ACLs — all codified | Zero; already exists |
| Isolation | Own address space, own routing | Shared with anything else in the account |
| Private DB subnet | Yes — no route to the internet | No — both subnets are public |
| NAT gateway for private subnets | Required (~$32/month + data) | Not needed |
| Fits a 1-week PoC | Overkill | Yes |

Because there is no NAT gateway in a default VPC, a private subnet would have **no internet access
at all**, which would break `dnf install` and the SSM agent. So we accepted using a public subnet
and compensated at the firewall layer: the instance has a public IP, but the security group allows
**no inbound traffic except 5432 from the app-tier SG**. That satisfies "reachable only from app
tier security group" while keeping the setup tiny and cheap.

When the project outgrows the PoC, the upgrade path is: create a custom VPC with private subnets,
add a NAT gateway (or VPC endpoints), move the DB there, and attach the app tier via the same SG
pattern.

## 5. Terraform, explained

### 5.1 What Terraform is and how it thinks

Terraform is a **declarative** infrastructure tool. You describe the *desired end state* in `.tf`
files; Terraform figures out the API calls needed to get there, and records what it created in a
**state file**.

Three commands matter:

- `terraform init` — download providers (the AWS plugin), initialize the backend and lock file.
- `terraform plan` — read state, read the real world, compute a diff, show "X to add, Y to change,
  Z to destroy." **Read-only.**
- `terraform apply` — execute that plan.

Terraform builds a **dependency graph** from references between resources (e.g. the instance
references the SG id), and creates things in dependency order. It also detects **drift** (someone
changed something by hand) and cycles (which we hit, see section 10).

### 5.2 File-by-file walkthrough

#### `versions.tf` and `providers.tf`

```hcl
terraform {
  required_version = ">= 1.9"
  required_providers {
    aws    = { source = "hashicorp/aws",    version = "~> 6.0" }
    random = { source = "hashicorp/random", version = "~> 3.6" }
  }
}

provider "aws" {
  region = var.aws_region
}
```

Providers are plugins that talk to APIs. We need `aws` (all the resources) and `random` (to
generate the DB password). `.terraform.lock.hcl` pins the exact provider versions and checksums;
it is committed to git so every machine resolves identical providers.

#### `variables.tf`

Inputs to the configuration, with defaults: `aws_region`, `project` (used in resource names),
`db_instance_type`, `db_volume_size`, `db_engine_version`, `db_name`, `db_username`,
`backup_retention_days`. Variables make the config reusable across environments without editing
code. Override them via `-var`, `terraform.tfvars`, or `TF_VAR_*` environment variables.

#### `locals.tf`

Computed values reused across resources. Ours is just a common tag map:

```hcl
locals {
  common_tags = { Project = var.project, ManagedBy = "terraform" }
}
```

Tags are not decoration in AWS — they drive billing reports and **DLM targeting** (the backup
policy finds the volume by its `Snapshot=daily` tag).

#### `data.tf`

Read-only discovery: the default VPC, its subnets, one concrete subnet, and the latest
Amazon Linux 2023 x86_64 AMI:

```hcl
data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]
  filter { name = "name"         values = ["al2023-ami-2023.*-x86_64"] }
  filter { name = "architecture" values = ["x86_64"] }
  filter { name = "state"        values = ["available"] }
}
```

Pinning the AMI by query instead of a hardcoded ID means the config keeps working as Amazon ships
new images. (The tradeoff: a `plan` six months from now could want to replace the instance because
the "latest" AMI changed.)

#### `security_groups.tf`

Two SGs and the critical rule:

```hcl
resource "aws_security_group_rule" "db_postgres_from_app" {
  type                     = "ingress"
  from_port                = 5432
  to_port                  = 5432
  protocol                 = "tcp"
  security_group_id        = aws_security_group.db.id
  source_security_group_id = aws_security_group.app_tier.id
}
```

Notice `source_security_group_id` instead of a CIDR. This means: *any network interface carrying
the app-tier SG may connect to 5432*. It survives IP changes, works across subnets, and needs no
knowledge of the app tier's addresses. The app-tier SG itself has no ingress rules — it is a
label/identity for now, and future ECS tasks will attach it.

**Gotcha we hit:** in Terraform, if you declare an `aws_security_group` and do not declare any
`egress` block, Terraform removes AWS's default allow-all egress. Our first apply left the DB SG
with zero egress, so the instance could not reach the internet, which meant `dnf` failed and the
SSM agent never registered. Fix: an explicit egress block (see section 10).

#### `secrets.tf`

```hcl
resource "random_password" "db" {
  length           = 32
  special          = true
  override_special = "!#$%&*()-_=+[]{}<>:?"
}

resource "aws_secretsmanager_secret" "db" {
  name                    = "${var.project}/db"
  recovery_window_in_days = 0
}

resource "aws_secretsmanager_secret_version" "db" {
  secret_id     = aws_secretsmanager_secret.db.id
  secret_string = jsonencode({
    username = var.db_username
    password = random_password.db.result
    engine   = "postgres"
    port     = 5432
    dbname   = var.db_name
  })
}
```

- `random_password` generates the value at apply time.
- `recovery_window_in_days = 0` means deleting the secret is immediate (fine for a PoC; avoids
  reserving the name for the default 30-day recovery window).
- The password ends up in **Terraform state**. State is sensitive and must be protected — see
  section 13.

#### `database.tf` — IAM

```hcl
data "aws_iam_policy_document" "ec2_assume" {
  statement {
    effect    = "Allow"
    actions   = ["sts:AssumeRole"]
    principals { type = "Service" identifiers = ["ec2.amazonaws.com"] }
  }
}
```

This is the **trust policy**: it says "the EC2 service may assume this role." Then we attach the
AWS-managed SSM policy and a one-secret inline policy, and wrap the role in an instance profile
(which is what EC2 actually consumes).

#### `database.tf` — the disk

```hcl
resource "aws_ebs_volume" "postgres_data" {
  availability_zone = data.aws_subnet.db.availability_zone
  size              = var.db_volume_size   # 20 GiB
  type              = "gp3"
  encrypted         = true
  tags = { Name = "...", Snapshot = "daily" }
  lifecycle { prevent_destroy = true }
}

resource "aws_volume_attachment" "postgres_data" {
  device_name = "/dev/sdf"
  volume_id   = aws_ebs_volume.postgres_data.id
  instance_id = aws_instance.postgres.id
}
```

The volume must be created in the exact AZ of the subnet, because EBS volumes cannot cross AZs.
`prevent_destroy = true` is a Terraform guard that refuses to plan the volume's deletion (see
section 12 for the operational consequence).

#### `database.tf` — the instance

```hcl
resource "aws_instance" "postgres" {
  ami                         = data.aws_ami.al2023.id
  instance_type               = var.db_instance_type          # t3.micro
  subnet_id                   = data.aws_subnet.db.id
  vpc_security_group_ids      = [aws_security_group.db.id]
  associate_public_ip_address = true
  iam_instance_profile        = aws_iam_instance_profile.postgres.name

  metadata_options {
    http_endpoint = "enabled"
    http_tokens   = "required"        # IMDSv2 only
  }

  root_block_device { volume_size = 8  volume_type = "gp3"  encrypted = true }

  user_data = templatefile("${path.module}/user_data.sh.tftpl", { ... })
  user_data_replace_on_change = true

  depends_on = [
    aws_secretsmanager_secret_version.db,
    aws_iam_role_policy.postgres_secret_read,
  ]
}
```

Reading the important lines:

- `associate_public_ip_address = true` — gives the host a public IPv4 so it can reach the internet
  outbound. It does **not** make PostgreSQL reachable; only the SG decides that (section 6).
- `http_tokens = "required"` — enforce **IMDSv2**, which mitigates SSRF-style attacks against the
  instance metadata service.
- `user_data` — the bootstrap script; `templatefile` injects values (secret ARN, VPC CIDR, etc.).
- `user_data_replace_on_change = true` — if the script text changes, Terraform replaces the
  instance (because user data only runs on first boot).
- `depends_on` — wait for the secret value and the IAM policy before creating the instance, so the
  boot script can read the secret on its first attempt.

#### `backup.tf`

```hcl
resource "aws_dlm_lifecycle_policy" "postgres_data" {
  state              = "ENABLED"
  execution_role_arn = aws_iam_role.dlm.arn
  policy_details {
    resource_types = ["VOLUME"]
    target_tags    = { Snapshot = "daily" }
    schedule {
      name        = "daily-7d"
      create_rule { interval = 24  interval_unit = "HOURS"  times = ["02:00"] }
      retain_rule { count = var.backup_retention_days }   # 7
      copy_tags   = true
    }
  }
}
```

The policy does not name the volume; it targets any volume with the tag `Snapshot=daily`. That
loose coupling is intentional — new volumes get backed up just by tagging them. The DLM service
needs its own IAM role (`dlm.amazonaws.com` trust + `AWSDataLifecycleManagerServiceRole`).

#### `outputs.tf`

Outputs surface values after apply: `db_instance_id`, `db_private_ip`, `db_security_group_id`,
`app_tier_security_group_id`, `db_secret_arn` (plus the pre-existing ECR/OIDC outputs). They are
how scripts and humans find the resource IDs, e.g.:

```bash
DB_ID=$(terraform -chdir=infra output -raw db_instance_id)
```

#### `user_data.sh.tftpl` — the bootstrap script

This is where Linux becomes PostgreSQL. It runs once, as root, on first boot:

```bash
#!/bin/bash
set -euo pipefail
exec > >(tee /var/log/user-data.log | logger -t user-data -s) 2>&1
```

- `set -euo pipefail`: fail fast on errors, undefined variables, and failed pipes.
- The `exec` line duplicates all output to `/var/log/user-data.log` and syslog — essential for
  debugging boot failures via SSM.

```bash
dnf install -y "postgresql${db_engine_version}-server" jq
```

Install PostgreSQL 16 server and `jq` (used later to parse the secret JSON). This is why the
instance needs outbound internet.

```bash
for _ in $(seq 1 60); do
  if [ -b "$DATA_DEVICE" ]; then break; fi
  sleep 5
done
[ -b "$DATA_DEVICE" ] || { echo "EBS device $DATA_DEVICE not found"; exit 1; }
```

Wait (up to 5 minutes) for the EBS volume to appear. This loop exists because cloud-init starts
before the volume attachment necessarily completes.

```bash
if ! blkid "$DATA_DEVICE" >/dev/null 2>&1; then mkfs.xfs "$DATA_DEVICE"; fi
mkdir -p "$DATA_MOUNT"
DATA_UUID=$(blkid -s UUID -o value "$DATA_DEVICE")
grep -q "$DATA_UUID" /etc/fstab || echo "UUID=$DATA_UUID $DATA_MOUNT xfs defaults,nofail 0 2" >> /etc/fstab
mountpoint -q "$DATA_MOUNT" || mount "$DATA_MOUNT"
chown -R postgres:postgres "$DATA_MOUNT"
```

Format only if empty (idempotent), mount the disk at `/var/lib/pgsql` (PostgreSQL's home on
Amazon Linux), persist the mount in `/etc/fstab` **by UUID** (device names are unstable), and give
the `postgres` user ownership. `nofail` ensures the instance still boots if the volume is absent.

```bash
PGDATA="$DATA_MOUNT/data"
if [ ! -f "$PGDATA/PG_VERSION" ]; then
  sudo -u postgres /usr/bin/initdb -D "$PGDATA"
fi

grep -q "^listen_addresses" "$PGDATA/postgresql.conf" || echo "listen_addresses = '*'" >> "$PGDATA/postgresql.conf"
grep -q "${vpc_cidr}" "$PGDATA/pg_hba.conf" || echo "host all all ${vpc_cidr} scram-sha-256" >> "$PGDATA/pg_hba.conf"
```

- `initdb` creates the database cluster — but only if `PG_VERSION` is missing, so re-running on an
  existing volume never wipes data.
- `listen_addresses = '*'` makes Postgres accept TCP connections (not just the local socket).
- The `pg_hba.conf` line allows password authentication (SCRAM) from the VPC CIDR. This is **defense
  in depth**: the security group is the primary wall; `pg_hba` is the second.

```bash
systemctl enable --now postgresql
```

Start Postgres and enable it at boot.

```bash
SECRET=""
for _ in $(seq 1 30); do
  if SECRET=$(aws secretsmanager get-secret-value --region "${aws_region}" --secret-id "${secret_arn}" ...); then break; fi
  sleep 10
done
DB_PASSWORD=$(echo "$SECRET" | jq -r .password)
```

Fetch the password from Secrets Manager using the instance role. The retry loop absorbs IAM
eventual-consistency right after role creation.

```bash
if ! sudo -u postgres psql -tAc "SELECT 1 FROM pg_roles WHERE rolname='${db_username}'" | grep -q 1; then
  sudo -u postgres psql -c "CREATE ROLE ${db_username} LOGIN PASSWORD '$DB_PASSWORD'"
else
  sudo -u postgres psql -c "ALTER ROLE ${db_username} WITH LOGIN PASSWORD '$DB_PASSWORD'"
fi
```

Create the application role (or rotate its password if it already exists). Finally, create the
database and restart the service.

**Why this design is nice:** the bootstrap is idempotent and data-safe. The EC2 instance can be
replaced freely; the script re-mounts the existing volume, sees `PG_VERSION`, skips `initdb`, and
re-applies configuration.

## 6. SSM: how it works, and why not SSH

### 6.1 How SSM actually works

1. The AMI ships the **SSM agent**.
2. The agent reads temporary AWS credentials from the **instance metadata** (that is why the
   instance profile matters).
3. It opens an **outbound HTTPS connection** to the SSM service and registers the instance as
   "managed," reporting its ID, OS, and agent version.
4. When you run `aws ssm start-session`, your CLI asks the SSM service to broker a session. The
   service signals the agent; the agent opens a **secure, bidirectional channel**; your terminal
   talks to the instance through it.
5. Every `StartSession` call is an IAM-authorized, CloudTrail-audited API call.

No inbound port, no listener exposed to the network, no key distribution.

### 6.2 What we used SSM for

| Use | Command | Why |
|---|---|---|
| Interactive shell | `aws ssm start-session --target <id>` | Inspect the host, run `psql` locally as `postgres` |
| Non-interactive checks | `aws ssm send-command --document-name AWS-RunShellScript` | Scripted verification (no TTY needed) |
| Port forwarding | `--document-name AWS-StartPortForwardingSession` | Reach the private DB from a laptop for Atlas |

Port forwarding is the clever one: your laptop's `localhost:15432` is tunneled over the SSM channel
to the instance, which then connects to `localhost:5432`. From AWS's point of view, all traffic
originates *on the instance* — so the DB security group never has to allow your laptop's IP.

### 6.3 Why SSM is safer than SSH

| Dimension | SSM | SSH |
|---|---|---|
| Inbound network port | None | 22 must be open |
| Public attack surface | Management plane not exposed | Port 22 reachable, brute-force target |
| Credentials | IAM temporary credentials, MFA-able | Long-lived private keys |
| Revocation | Remove IAM permission — instant | Find and rotate every copy of a key |
| Audit | CloudTrail + optional session logs to S3/CloudWatch | Local `sshd` logs only |
| Key sprawl | None | Keys get copied across laptops |

For a database box, "no inbound ports" is a large win. On this instance `sshd` is running by
default, but nothing can reach it: no port 22 rule exists in the DB SG, and there is no key pair.

### 6.4 What SSM does *not* protect you from

The trust boundary moves to **IAM**. Anyone with `ssm:StartSession` on that instance gets a
root-capable shell and can therefore reach the database locally (and can also port-forward to it).
So the security controls that matter are: keep the set of principals who can start sessions small,
require MFA, and turn on session logging. SSM is safer *than SSH*, but only if you do not also open
SSH "just in case."

## 7. The public IP question

The question "how did we expose the DB IP to the public?" contains a misconception worth
untangling.

### 7.1 What we actually did

We set `associate_public_ip_address = true` on the EC2 instance. That attaches a **public IPv4
address to the virtual machine** (here, `13.215.251.224`). It does not "expose the database."

### 7.2 What is exposed, and what is not

Exposure is decided entirely by the security group:

```
DB SG ingress rules:        tcp/5432 from sg-0f962929f956ecf62   (app tier)
                            (nothing else)
DB SG egress rules:         all outbound
```

So from the internet's perspective:

- **No inbound port is allowed** on that public IP — not 22, not 5432, nothing.
- **Outbound** traffic works, which is what `dnf` and the SSM agent need.

The public IP exists to solve an *outbound* problem (default VPC, no NAT gateway), not to provide
inbound access. If we had used a private subnet with a NAT gateway, we would not need it at all.

### 7.3 Proving it — the negative test

From a laptop outside AWS:

```bash
python3 -c "import socket; s=socket.socket(); s.settimeout(5); print(s.connect_ex(('13.215.251.224',5432)))"
# non-zero (times out) => filtered by the security group
```

A timeout (rather than "connection refused") is the signature of a firewall silently dropping
packets — exactly what an SG with no matching allow rule does.

### 7.4 IMDSv2

Because the instance has a public IP, the metadata service (IMDS) deserves a thought. If an
attacker could trick the instance into making an HTTP request to `169.254.169.254`, they might
steal the instance role's credentials. That is why we require **IMDSv2** (`http_tokens = "required"`):
tokens are session-based and require a PUT request with a TTL, which raises the bar significantly
for SSRF-style abuse.

## 9. Bugs we hit (and the lessons)

These are the most valuable part of the exercise.

### 9.1 The security group egress gotcha

**Symptom:** the instance never appeared in SSM; `user_data` died at `dnf install`.

**Cause:** Terraform's `aws_security_group` removes the default allow-all egress rule if you don't
declare any `egress` block. So the DB SG had no outbound traffic at all; the instance could not
reach the internet or the SSM endpoints.

**Fix:** declare egress explicitly.

**Lesson:** in AWS, a security group always has *two* directions. "I didn't add an allow rule" and
"traffic is allowed by default" are not the same thing; Terraform makes the default explicit
(empty) for you. Always check both directions when debugging connectivity.

### 9.2 The systemd unit name

**Symptom:** `Failed to enable unit: Unit file postgresql-16.service does not exist.`

**Cause:** we assumed the Fedora-style versioned unit. Amazon Linux 2023 ships a single
`postgresql.service` whose `PGDATA` is `/var/lib/pgsql/data` — which is exactly where we mounted
the EBS volume.

**Fix:** `systemctl enable --now postgresql`.

**Lesson:** package layout is distribution-specific. Verify unit names on the actual image instead
of assuming; debugging from the `user_data` log over SSM is how we found it.

### 9.3 A dependency cycle

**Symptom:** `Error: Cycle: aws_instance.postgres, aws_volume_attachment.postgres_data`.

**Cause:** the instance listed the attachment in `depends_on`, while the attachment referenced the
instance's ID. Terraform's graph cannot topologically sort that.

**Fix:** remove the `depends_on`; the attachment naturally follows the instance, and the boot
script's wait loop tolerates the small race until `/dev/sdf` appears.

**Lesson:** Terraform dependencies must form a DAG. When two resources genuinely need each other,
one side must resolve the race at runtime rather than at graph time.

### 9.4 Terraform lifecycle arguments must be literals

**Symptom:** `Variables may not be used here` for `prevent_destroy = var.db_volume_prevent_destroy`.

**Cause:** Terraform's `lifecycle` meta-arguments are evaluated statically; they cannot be driven
by input variables.

**Fix:** hardcode `prevent_destroy = true` (and pay the small teardown tax), or remove the guard.
We chose the hardcoded guard.

**Lesson:** not everything in Terraform is parameterizable. Know which features are static
configuration vs. runtime values.

### 9.5 DLM description validation

**Symptom:** `invalid value for description` on the DLM policy.

**Cause:** the DLM API validates the description against a restricted character set (a trailing
period was enough to fail it).

**Fix:** simplify the description.

**Lesson:** AWS APIs often impose stricter validation than you expect; error text usually points at
the offending field.

## 10. Migrations: how the app talks to the database

The schema is versioned with **Atlas**. Migration files live in `migrations/`, and Atlas records
what it has applied in a special table so it never runs the same migration twice.

### 10.1 The `ec2` Atlas environment

`atlas.hcl` gained:

```hcl
env "ec2" {
    url = getenv("EC2_DATABASE_URL")
    dev = "docker://postgres/16/dev"
    src = "file://migrations/schema.hcl"
    migration { dir = "file://migrations" }
}
```

Two details:

- Atlas does not interpolate bare `${VAR}` from the shell; it provides `getenv("VAR")` for that.
- `dev` is a throwaway database Atlas uses to validate/plan migrations; `url` is the real target.

### 10.2 Reaching a private database from a laptop

The DB has no public reachability. So:

1. Open an SSM port-forward: laptop `15432` -> instance `5432`.
2. Export a connection string with the percent-encoded password (the generated password can contain
   URL-special characters like `#`, `?`, `@`, so encoding is mandatory).
3. `atlas migrate apply --env ec2`.

This is the same pattern a developer would use against RDS in a private subnet, and it is the
reason SSM port forwarding is a standard production tool — not just a PoC convenience.

### 10.3 Verifying a migration

```sql
-- what has been applied
SELECT version, description, executed_at
FROM atlas_schema_revisions.atlas_schema_revisions
ORDER BY version;
```

Expect 5 rows matching the 5 files in `migrations/`. If a migration had failed, its row would show
a non-null `error` column. We also verified the app tables directly:

```
products, inventory_batches, users, production_orders,
production_order_line_items, stock_transactions, refresh_tokens
```

## 11. Backups and cost

### 11.1 Snapshots

DLM takes a snapshot daily at 02:00 UTC and retains 7. Snapshots are **incremental**: the first is
a full copy, subsequent ones store only changed blocks, so steady-state cost is far below
`volume_size × 7`.

Important limitations to understand:

- EBS snapshots are **crash-consistent**, not transaction-log backups. PostgreSQL can recover from
  a crash-consistent disk image (it is designed to survive power loss), but this is **not** point-in-time
  recovery. A production system would also archive WAL (e.g. `pgBackRest`/WAL-G) for PITR.
- Snapshots created by DLM are **not managed by Terraform**. Deleting the stack removes the policy
  but leaves the snapshots billing until deleted.

### 11.2 Cost (ap-southeast-1, at the time of writing)

| Item | Rate | Monthly |
|---|---|---|
| `t3.micro` Linux on-demand | $0.0132/hr | ~$9.64 |
| gp3 storage (20 GiB data + 8 GiB root) | $0.096/GB-mo | ~$2.69 |
| EBS snapshots (~20 GB, incremental) | $0.05/GB-mo | ~$1.00 |
| Public IPv4 (in-use) | $0.005/hr | ~$3.65 |
| Secrets Manager (1 secret) | $0.40/secret-mo | ~$0.40 |
| DLM / SSM | free | $0.00 |
| **Total** | | **~$17/month** |

For a one-week PoC that is roughly **$4**. The largest levers are turning the instance off when
idle (EC2 + public IPv4 stop charging; EBS keeps charging) and, for longer-lived use, Graviton or
Savings Plans.

### 11.3 The budget alarm

An AWS Budget (`fmis-api-monthly`, $5/month) alerts at 80% and 100% actual and 100% forecasted,
publishing to the `Billing_Alert` SNS topic. Budgets are account-level and were configured with the
CLI, not Terraform, because they are cost governance rather than application infrastructure.

## 12. Security posture (summary)

| Control | Choice | Rationale |
|---|---|---|
| DB network access | SG allowing 5432 only from the app-tier SG | Satisfies the acceptance criterion; no CIDR-based trust |
| Admin access | SSM only; no SSH port, no key pair | No inbound management surface; IAM-authorized and auditable |
| Credentials | Random password in Secrets Manager | Never hardcoded in the AMI or user data |
| Instance AWS access | Least-privilege role (SSM core + one secret read) | Blast radius limited if the instance is compromised |
| Metadata service | IMDSv2 required | Mitigates SSRF credential theft |
| Disk encryption | EBS volumes encrypted at rest | Data-at-rest protection |
| Database auth | SCRAM password auth restricted to VPC CIDR in `pg_hba` | Defense in depth behind the SG |
| Backups | DLM daily, 7-day retention | Meets the "snapshot backup policy" criterion |

Known gaps (acceptable for a PoC, not for production):

- Terraform state is **local** and contains the generated password in plaintext. It is gitignored,
  but the production path is an encrypted remote backend (S3 + KMS) with state locking.
- The DB has a public IP (needed due to default VPC + no NAT). A custom VPC removes it.
- No TLS on the Postgres connection (`sslmode=disable`); acceptable inside a VPC, but production
  should enable TLS.
- No WAL archiving / PITR.
- Single AZ, single instance: no failover.

## 13. Lifecycle: pause, resume, teardown

**Pause (keep data):** stop the instance.

```bash
aws ec2 stop-instances --region ap-southeast-1 \
  --instance-ids "$(terraform -chdir=infra output -raw db_instance_id)"
```

Compute and public-IP charges stop; EBS and snapshots keep billing. Data persists on the volume.
On start, PostgreSQL comes back automatically (`systemctl enable`), the **private IP is unchanged**,
but the **public IP changes** (irrelevant for SSM, which targets the instance ID).

**Teardown (delete everything):**

1. The data volume has `prevent_destroy = true`, so `terraform destroy` will refuse. Remove the
   guard first (or `terraform state rm` the volume).
2. DLM snapshots outlive the stack. Delete them or they keep costing money:

```bash
aws ec2 describe-snapshots --owner-ids self \
  --filters Name=tag:Snapshot,Values=daily --region ap-southeast-1 \
  --query 'Snapshots[].SnapshotId' --output text | xargs -n1 \
  aws ec2 delete-snapshot --region ap-southeast-1 --snapshot-id
```

3. `terraform -chdir=infra destroy`.
